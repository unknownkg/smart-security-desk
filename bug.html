Проверка статуса инцидента

По методичке необходимо временно воспроизвести ошибочное поведение API в изолированной версии, зарегистрировать дефект, восстановить проверку и оформить исправление через GitHub workflow.

Запрос
PATCH /api/incidents/:id
Важность
Средняя
Тест
TC-06
Статус
Issue закрыт, PR слит

Последовательность работы

Рабочая ветка main не содержит намеренного дефекта.

  1. 01
    ОбнаружениеИзолированная проверка выполнена
  2. 02
    IssueIssue #12 закрыт
  3. 03
    ИсправлениеPR #13 слит в учебную ветку
  4. 04
    ПроверкаHTTP 400 подтверждён

Ожидаемое поведение

Допустимые значения: new, in_progress и resolved. Значение closed должно быть отклонено.

PATCH /api/incidents/:id
{
  "status": "closed"
}
Ожидаемый ответ400 Bad Request

Воспроизведение дефекта

  1. В изолированной версии временно отключена проверка статуса.
  2. Отправлен PATCH-запрос со значением closed.
  3. API ошибочно вернул HTTP 200 и сохранил недопустимый статус.
  4. Фактический ответ сохранён в доказательствах.
Открыть ответ до восстановления ↗

Регистрация ошибки

Incident accepts invalid status

Expected
HTTP 400 Bad Request
Actual
HTTP 200 OK, статус closed принят
Severity
Medium

Шаги: создать инцидент и отправить PATCH со статусом closed при временно отключённой проверке. Открыть GitHub Issue #12 ↗

Исправление и проверка

После восстановления проверки тот же запрос получил HTTP 400. Дефект исправлен в ветке fix/incident-validation, TC-06 повторён, PR слит в exercise/incident-validation.

Вывод

Валидация не допускает некорректные данные, а негативные тесты проверяют отказ на неверном вводе. Issue фиксирует дефект, отдельная ветка изолирует исправление, а Pull Request позволяет проверить изменение до его слияния.

Итог: ответы 200 и 400 подтверждены на изолированной базе; Issue #12 закрыт, PR #13 слит в учебную ветку.
